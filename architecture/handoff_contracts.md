# BooksFactory — Контракты передачи (Handoff Contracts)

> **⚠️ Статус документа — в переходе (обновлено 2026-04-24, Ф3a из аудита §13).**
>
> Контракты 1–5 (ниже) описывают **section-by-section** цепочку — текущую форму для идущих проектов. Они остаются рабочими до завершения Ф7/Ф8 ТЗ.
>
> Контракты 6–8 (добавлены 2026-04-24) покрывают **beat-by-beat** слой: writer↔critic loop, любая фаза↔controller, compiler→session. Они активируются по мере выполнения Ф1, Ф3, Ф7, Ф8 ТЗ. На момент 2026-04-24 рабочими являются 6 (critic уже создан в Ф1) и 8 (compiler создан в Ф3). Контракт 7 работает с момента создания controller-а (2026-04-23 вечер).
>
> Контракт 9 (добавлен 2026-04-26 в рамках P2-4) описывает **выход из writer-loop**: coordinator передаёт собранную главу в Editor → Humanizer. Humanizerator никогда не получают beat-файлы напрямую — это инвариант пайплайна.
>
> После Ф7/Ф8 контракт 1 (PM → Писатель) расщепляется на цепочку: **Researcher → Material-Author → Planner → Compiler → Coordinator → Writer↔Critic loop → Editor**. Расщепление оформится отдельным апдейтом этого документа в Ф8.

## Принцип работы контрактов

**Контракт** — набор обязательных условий, которые должны быть выполнены перед передачей артефакта следующей роли. 

**Правило возврата**: артефакт, не соответствующий контракту, возвращается на предыдущую роль с указанием конкретного нарушения. Текущая роль не «чинит за соседа» — это нарушает изоляцию ролей и маскирует системные ошибки.

**Правило явности**: нарушение контракта формулируется конкретно: не «MATERIAL неполный», а «отсутствует beat sheet в секции 3 — возврат к PM».

Термины: см. `architecture/shared_vocabulary.md`.

## Цепочка передачи

```
PM ──→ Писатель ──→ Редактор ──→ Писатель (применение правок)
                                      │
                                      ▼
                               Гуманизатор ──→ Финал
```

## Контракт 1: PM → Писатель

### Входящий артефакт

**Один файл** — `Session_KapitelNN.md`. Самодостаточный. Писатель больше ничего не читает.

Структура файла (см. `architecture/shared_vocabulary.md`, слой B):
- **Часть 1: MATERIAL-блок** — что писать (секции, beat sheets, арены, источники главы)
- **Часть 2: Технический протокол** — T1 (уникальные поля главы) + T2–T12 (статический протокол из `session_template_XX.md`)

Предусловие существования: слой A книги полностью собран и утверждён пользователем (см. `skills/project-manager/SKILL.md`, research-режим).

### Обязательные поля MATERIAL-блока

| Поле | Описание | Пример |
|------|----------|--------|
| YAML frontmatter | `глава`, `название`, `целевой_объём`, `язык`, `книга`, `создан`, `статус` | `глава: 05` |
| `секции` | H2-блоки с названиями и целевыми объёмами | `### Секция 2: Лояльность из страха — 1800 слов` |
| `микрорежим` секции | Тональный регистр, из `stil_und_ton_XX.md` | `Микрорежим: анатомическая точность` |
| `beat_sheet` секции | 5–7 beats с word budgets и конкретными задачами | `1. Диагностическая посылка — 200 слов: назвать механизм без объяснения` |
| `арены` главы | Коды из `arenen_pool_XX.md` с описанием момента и типом декомпрессии | `ARENA-07: офис после увольнения — Форма 2` |
| блок «Для углублённого изучения» | Копипаст из `quellen_pool_XX.md` для этой главы | Автор, название, год, уникальный фокус для главы |

### Обязательные поля T1

| Поле | Описание |
|------|----------|
| Выходной файл | Имя финального `.md` по naming convention (из `anweisungen_XX.md`) |
| Калибровочные главы | Три предыдущие (или явные исключения) |
| Уникальные правила главы | Отклонения от стандартного протокола или «Нет уникальных правил» |

### Обязательные поля T2–T12

Побайтовая копия из `session_template_XX.md` книги (всё ниже маркера `---BEGIN_PROTOCOL---`). Любые отклонения от этой побайтовой копии — ошибка PM.

### Предусловия для старта Писателя

- [ ] Session-файл начинается YAML-frontmatter MATERIAL-блока
- [ ] Все секции MATERIAL-блока имеют beat sheet (минимум 5 beats) и микрорежим
- [ ] Целевой объём главы задан
- [ ] Блок «Для углублённого изучения» присутствует в MATERIAL-блоке
- [ ] T1 заполнен тремя конкретными значениями (не placeholder'ы)
- [ ] T2–T12 побайтово идентичны `session_template_XX.md` книги
- [ ] Session-файл заканчивается маркером «Конец технического протокола.» (или эквивалентом книги)

### Критерии возврата к PM

| Нарушение | Формулировка возврата |
|-----------|----------------------|
| Нет beat sheet в секции N | «Отсутствует beat sheet в секции N — возврат к PM» |
| Нет микрорежима в секции N | «Не задан микрорежим в секции N — возврат к PM» |
| Пустой блок «Для углублённого изучения» | «Блок источников пустой — возврат к PM» |
| T1 содержит placeholder | «T1 не заполнен для главы N — возврат к PM» |
| T2–T12 не соответствуют session_template_XX.md | «Техпротокол отклоняется от session_template — возврат к PM» |
| Файл разбит на MATERIAL + Session отдельно (старая карта) | «Требуется единый Session_KapitelNN по актуальной карте — возврат к PM» |

## Контракт 2: Писатель → Редактор

### Входящий артефакт

`NN_Glava_XX_Title.md` — рукопись главы с YAML frontmatter.

### Обязательные поля главы

| Поле | Требование |
|------|-----------|
| `status` | `draft` или выше |
| `word-count` | Заполнен (реальный подсчёт) |
| `last-edited` | Дата последнего изменения |
| Структура | Все секции из MATERIAL присутствуют |
| Объём | В диапазоне ±15% от целевого (жёсткий контракт) |

| Получает | Не получает |
|---------|-------------|
| Черновик всех секций | Незаконченные секции |
| Список источников в финальном блоке | Отсутствующий блок источников |
| Корректный frontmatter | Файл без YAML |

### Критерии возврата к Писателю (из Редактора)

| Нарушение | Действие |
|-----------|---------|
| Секция отсутствует или обрезана | Возврат к Писателю |
| Объём < 85% от целевого | Возврат к Писателю |
| Блок источников отсутствует | Возврат к Писателю |

## Контракт 3: Редактор → Писатель (применение правок)

### Формат отчёта Редактора

Редактор передаёт **отчёт**, не исправленный текст. Отчёт содержит:

```markdown
## Отчёт редактуры — Глава NN

### Летальные нарушения (блокируют переход к Гуманизатору)
| # | Тип | Цитата | Нарушение | Действие |
|---|-----|--------|-----------|---------|
| 1 | failure_mode | «текст» | FM-03: демонизация | Переписать |

### Замечания (некритичные)
| # | Цитата | Проблема | Предложение |
|---|--------|----------|------------|

### Статус передачи
- [ ] Все летальные нарушения устранены → можно передавать Гуманизатору
```

### Что Писатель делает с отчётом

1. Исправляет летальные нарушения (обязательно)
2. Рассматривает замечания (на усмотрение)
3. Возвращает главу Редактору на повторную проверку
4. После «чисто» от Редактора — глава идёт к Гуманизатору

### Критерии возврата к Редактору

Писатель **не передаёт Гуманизатору** главу с летальными нарушениями. Только после повторного «чисто» от Редактора.

### Предусловия (все должны быть выполнены)

- [ ] Глава прошла все летальные проверки Редактора (получила статус «чисто»)

`NN_Glava_XX_Title.md` со статусом `editing` или `review` (после применения правок Редактора).

### Что Гуманизатор получает

Главу с чистой смысловой структурой, без failure modes Редактора, с сохранённым голосом автора, готовую к удалению ИИ-отпечатков.

### Критерии возврата к Писателю

| Нарушение | Действие |

| Глава не прошла летальные проверки Редактора | Возврат к Писателю |

| Смысловая структура не зафиксирована (противоречия, незавершённость аргументации) | Возврат к Редактору |

## Контракт 6: Writer ↔ Critic (per-beat loop)

> **Beat-by-beat слой. Активен с Ф1 (critic создан 2026-04-23). Полностью включается после Ф7/Ф8.**

### 6.1 Writer → Critic (первичная передача)

Координатор (loop-оркестратор, `bf-coordinator`) передаёт critic-у **три поля** в одном вызове:

```json
{
  "beat_description": {
    "beat_id": 5,
    "section": "§4 Центральная сцена",
    "thema": "…",
    "target_words": 500,
    "style_anchor": "REFERENZ маркер №5",
    "material_refs": ["…"],
    "constraints": ["…"],
    "street_calibration": true,
    "target_provocation": "среда",
    "is_last_beat": false
  },
  "beat_text": "<полный текст beat-а от writer-а, без обрамления тегов>",
  "actual_words": 520
}
```

Critic **не доверяет** полю `actual_words` — пересчитывает сам. Отличие от writer-подсчёта фиксирует во флагах.

### 6.2 Обязательные поля writer-ответа

Writer возвращает строго теговый формат (см. `_TZ_WRITER_BEAT_BY_BEAT.md` §2.3):

```
<beat_text>
(проза beat-а)
</beat_text>

<word_count>NNN</word_count>

<notes>
(опционально)
</notes>
```

| Поле | Тип | Валидность |
|------|-----|-----------|
| `<beat_text>` | строка | непустая, ≥ 0.85 × target_words |
| `<word_count>` | int | ≥ 1 |
| `<notes>` | строка | опционально |

Если теги отсутствуют или битые — координатор **не передаёт в critic**, а запрашивает writer-а повторно (это не revise, это re-emit).

### 6.3 Critic → Coordinator (JSON-вердикт)

Critic возвращает строго JSON (см. `bf-critic.md` §«Формат ответа»):

```json
{
  "beat_id": 5,
  "action": "accept" | "revise" | "rewrite",
  "actual_words": 520,
  "target_words": 500,
  "flags": ["volume_short", "anaphora_storm"],
  "notes": "конкретно что исправить"
}
```

| Action | Семантика | Последствие в loop |
|--------|-----------|---------------------|
| `accept` | 0 блокирующих флагов | Beat сохранён в scratchpad, переход к следующему |
| `revise` | 1+ флаг, чинится за 1–3 итерации | Повторный вызов writer-а в revise-режиме (§2.7 ТЗ) |
| `rewrite` | 3+ флагов / style_drift<50 / volume_critical_short | Эскалация автору, возврат к planner-у |

### 6.4 Предусловия старта loop-а

- [ ] beat_plan.json валиден, все beat-ы имеют `target_words` и `thema`.
- [ ] Session_compiled.md собран compiler-ом и содержит все маркеры (T1–T12, BEGIN_REFERENCE/VERBOT/CALIBRATION/PROTOCOL).
- [ ] `tonal_compass.md` книги содержит `reference_chapter` и читаемый эталон голоса.
- [ ] Критик доступен (`bf-critic.md` существует, tools: Read).

### 6.5 Критерии возврата

| Нарушение | Возврат |
|-----------|---------|
| Writer вернул без тегов | Coordinator → Writer (re-emit, не считается итерацией) |
| Critic вернул не-JSON | Coordinator → Critic (re-emit) |
| `max_iterations_on_current = 3` без accept | Эскалация автору, STOP |
| `action: "rewrite"` | Возврат к `bf-planner` (план beat-а некорректен) |

## Контракт 7: Любая фаза → Controller

> **Meta-слой. Активен с 2026-04-23 (controller создан по запросу автора как замена переспрашивания DoD).**

### 7.1 Что получает Controller

Координатор (или автор напрямую) вызывает `bf-controller` с тремя полями:

```json
{
  "phase": "Ф<N>",
  "artifact_paths": [
    "<absolute path к созданному/изменённому файлу>"
  ],
  "tz_references": [
    "_TZ_WRITER_BEAT_BY_BEAT.md §5.1 строка Ф<N>",
    "_HANDOFF_FACTORY_TUNING_2026-04-23_PART2.md §<N>"
  ]
}
```

### 7.2 Что возвращает Controller

Строго JSON по схеме `bf-controller.md`:

```json
{
  "phase": "Ф<N>",
  "action": "accept" | "warn" | "block",
  "dod_checks": { "artifact_exists": true, ... },
  "runtime_checks": { "tool_capability": true, ... },
  "hang_checks": { "exit_paths_covered": true, ... },
  "dry_run": { "executed": false | true, ... },
  "blockers": [],
  "warnings": [],
  "notes": "…"
}
```

| Action | Семантика | Последствие |
|--------|-----------|-------------|
| `accept` | Все 4 уровня ок | Координатор помечает фазу как ✅ в handoff |
| `warn` | DoD ок, но есть несинхрон (fingerprint, таблицы) | Координатор исправляет warnings, не вызывает автора |
| `block` | Любой из 4 уровней дал критическое нарушение | **Эскалация автору.** Координатор не продолжает следующую фазу |

### 7.3 Обязательное условие

Controller вызывается **после каждой фазы** Ф0–Ф13 ТЗ. Без controller-вердикта `accept`/`warn` фаза не считается закрытой в handoff.

Для Ф7/Ф8 controller обязан провести **dry-run** блок (симуляция accept/revise/rewrite/compile-путей). Если `dry_run.executed == false` на Ф7/Ф8 — автоматический block.

### 7.4 Критерии возврата

| Нарушение | Возврат |
|-----------|---------|
| Controller не прочитал артефакт (Read fail) | Координатор повторяет вызов с полным путём |
| Controller вернул не-JSON | Координатор перезапускает |
| Action `block` | **Стоп конвейера. Эскалация автору.** |

## Контракт 8: Compiler → Coordinator (compiled Session)

> **Beat-by-beat слой. Активен с Ф3 (compiler создан 2026-04-24). Полностью подключается в Ф6/Ф8.**

### 8.1 Что получает Compiler

Координатор передаёт в промпте (компилятор не сочиняет пути, см. `bf-compiler.md` §«Вход»):

```json
{
  "book_root": "<absolute>",
  "chapter_number": 1,
  "material_path": "<book_root>/_drafts/MATERIAL_Glava_01.md",
  "beat_plan_path": "<book_root>/_drafts/01_beat_plan.json",
  "tonal_compass_path": "<book_root>/tonal_compass.md",
  "verbot_liste_path": "<book_root>/verbot_liste.md" | null,
  "reference_chapter_path": "<path из tonal_compass>",
  "calibration_paths": ["<previous chapter 1>", "<previous chapter 2>"] | [],
  "session_template_path": "<book_root>/Session_TEMPLATE.md",
  "output_path": "<book_root>/_drafts/01_session_compiled.md"
}
```

### 8.2 Что возвращает Compiler (успех)

```json
{
  "status": "compiled",
  "output_path": "<absolute>",
  "size_bytes": NNNNN,
  "markers_present": ["T1", "T2", ..., "PROTOCOL"],
  "warnings": ["T2 запреты: секция не найдена в tonal_compass"],
  "chapter_target_words": 6000,
  "beats_count": 15,
  "sum_target_words_beats": 6780
}
```

### 8.3 Что возвращает Compiler (ошибка)

Строго пятипрефиксная семантика:

| Префикс | Причина | Координатор делает |
|---------|---------|---------------------|
| `COMPILER_PREFLIGHT_FAILED` | Вход не читаем | Эскалация к researcher/material-author/planner — какой артефакт отсутствует |
| `COMPILER_BEAT_PLAN_INVALID` | JSON beat-плана невалиден | Возврат к planner |
| `COMPILER_BEAT_PLAN_STRUCTURE_BROKEN` | JSON валиден, инварианты нарушены | Возврат к planner с конкретным нарушением |
| `COMPILER_MARKER_MISSING` | После сборки маркер отсутствует в output | Повторная сборка (compiler сам удалил частичный output) |
| `COMPILER_WRITE_FAILED` | Write не прошёл (права, диск) | Эскалация автору |

### 8.4 Предусловия

- [ ] Researcher завершил `_outline.md` и `tonal_compass.md`, оба одобрены.
- [ ] Material-author выдал `MATERIAL_Glava_NN.md`.
- [ ] Planner выдал `NN_beat_plan.json` с валидной структурой (массив beats, sum_target_words = 1.13 × chapter_target ±5%).
- [ ] Reference chapter существует по пути из `tonal_compass.reference_chapter`.

### 8.5 Critical invariant

Compiler **не оставляет частичный output на диске**. Если Self-check (шаг 5 `bf-compiler.md`) обнаружил отсутствующий маркер — output удаляется, возвращается `COMPILER_MARKER_MISSING`. Это защита от ситуации, когда writer-loop запускается с битым Session-файлом.

### 8.6 Критерии возврата

| Нарушение | Возврат |
|-----------|---------|
| Любой префикс ошибки | Координатор не запускает writer-loop, маршрутизирует по таблице §8.3 |
| Compiler вернул проза-текст вместо JSON | Автоматический re-emit; если повторно — эскалация автору (contract-drift у compiler-а) |

## Контракт 9: Editor → Humanizer (beat-by-beat пайплайн)

> **Beat-by-beat слой. Активен с 2026-04-26 (P2-4).** Описывает выход главы из writer-loop'а: единый сборный артефакт идёт в Editor, потом в Humanizer. Humanizer **никогда** не работает с beat-файлами — это инвариант.

### 9.1 Coordinator → Editor

**Вход**: единый файл `<book>/_drafts/glava_NN.md`, собранный coordinator-ом из всех принятых beats после writer-loop-а. **Один файл, не N beat-файлов.**

```json
{
  "chapter_path": "<book>/_drafts/glava_NN.md",
  "status": "draft",
  "beats_assembled_count": 15,
  "tonal_compass_path": "<book>/tonal_compass.md",
  "verbot_liste_path": "<book>/verbot_liste.md" | null,
  "reference_chapter_path": "<path>"
}
```

Editor читает эти артефакты, но работает только с `chapter_path`. Beat-файлы (`beat_NN_K.md` или подобные) — внутренняя кухня writer-loop'а, в Editor они **не передаются**.

### 9.2 Что Editor делает

- Точечные правки (≤5 точек, см. `architecture/writing_control.md`).
- Чек-лист по erbot_liste.md книги и rchitecture/writing_control.md.
- **Не переписывает прозу.** Edit-инструмент запрещён (см. CLAUDE.md §«Правила, которые нельзя нарушать», п. 4).
- Возвращает отчёт автору / refiner-у.

### 9.3 Editor → Author/refiner (отчёт)

Формат отчёта — как в Контракте 3 (летальные нарушения + замечания + чек-лист статуса передачи). После применения правок author/refiner — повторная проверка Editor-ом.

### 9.4 Editor → Coordinator (clean)

После того как Editor подтвердил «чисто»:
- Создаётся `<book>/_drafts/glava_NN_clean.md` (или `glava_clean.md` по convention книги).
- Статус главы переходит `draft → review → clean` (review — промежуточный, см. `production_state.md`).
- Coordinator обновляет `production_state.md`.

### 9.5 Coordinator → Humanizer

**Вход**: `<book>/_drafts/glava_NN_clean.md` со статусом `clean`. Один файл.

```json
{
  "chapter_path": "<book>/_drafts/glava_NN_clean.md",
  "status": "clean",
  "language": "ru" | "de" | "en",
  "tonal_compass_path": "<book>/tonal_compass.md"
}
```

Humanizer вызывает соответствующий языковой модуль (`skills/humanizer/<lang>/`). Результат — `glava_NN_humanized.md` со статусом `humanized` (готов к финалу (Контракт 5).

### 9.6 Инвариант пайплайна

**Humanizer никогда не получает beat-файлы.** Beat-файлы существуют только внутри writer-loop-а (Ф8). Любая попытка передать `beat_NN_K.md` напрямую в Humanizer — нарушение контракта; coordinator должен сначала собрать главу.

### 9.7 Возврат в beat-loop (исключительный путь)

Если Editor находит проблему, локализованную в **одном beat'е** (например, тематический дрейф или нарушение style_anchor только в beat #5), Editor может **запросить через coordinator переоткрытие конкретного beat'а** в writer-loop-е.

Формат запроса:

```json
{
  "action": "reopen_beat",
  "beat_id": 5,
  "reason": "style_drift в beat #5: полный отрыв от REFERENZ маркера",
  "scope": "single_beat",
  "preserve_old_glava_path": "<book>/_drafts/_history/glava_05_v<unix_timestamp>.md"
}
```

Coordinator:
1. **Перед откатом статуса** сохраняет текущий `<book>/_drafts/glava_NN.md` в `<book>/_drafts/_history/glava_NN_v<unix_timestamp>.md` (поле `preserve_old_glava_path` запроса). Это позволяет автору сравнить версии и откатить решение `reopen_beat`, если правка Editor-а оказалась ошибочной.
2. Откатывает статус главы `draft → compiled` (decomposition: `beat-5-accepted → beat-5-draft`).
3. Запускает writer-loop **только для beat #5** (Ф8).
4. После accept — пересобирает `glava_NN.md`, повторяет Контракт 9.1.

**Это редкое исключение, не норма.** Норма — Editor работает с собранной главой и возвращает отчёт автору/refiner-у (Контракт 9.3). Возврат в beat-loop оправдан только когда правка по тексту главы невозможна без переписывания целого beat'а.

### 9.8 Критерии возврата

| Нарушение | Возврат |
|-----------|---------|
| `chapter_path` не существует / пустой | Coordinator → возврат на этап сборки `glava.md` (writer-loop exit) |
| Editor получил список beat-файлов вместо единого `glava.md` | Контракт-нарушение; Coordinator перепроверяет, был ли запущен сбор после writer-loop |
| Humanizer получил статус ≠ `clean` | Возврат к Editor-у (повторная проверка) |
| Humanizer получил beat-файл | **Контракт-нарушение пайплайна.** Стоп, эскалация автору (баг coordinator-а) |
| `reopen_beat` запрос без `beat_id` или с `scope ≠ "single_beat"` | Coordinator отклоняет запрос; Editor либо формирует корректный, либо обходится отчётом |

### 9.9 Связь со статусной моделью

| Этап Контракта 9 | Статус главы (по `production_state.md`) |
|-------------------|-----------------------------------------|
| 9.1 (вход в Editor) | `draft` |
| 9.3 (Editor → author) | `review` |
| 9.4 (Editor → Coordinator) | `clean` |
| 9.5 (вход в Humanizer) | `clean` |
| После Humanizer | `humanized` |

Подстатусы `compiled`, `beat-N-draft`, `beat-N-accepted` относятся к фазе **до** Контракта 9 (внутри writer-loop, Ф8). См. `.claude/memory/production_state.md` секция «Декомпозиция draft-фазы».

## Сводная таблица статусов главы

> Финализирована 2026-04-25 (P3-2). Источник истины: `.claude/memory/production_state.md`.
> Базовая последовательность: `(нет файла) → outline-ready → material-draft → draft → review → clean → humanized → final`.

| Статус | Кто ставит | Что означает |
|--------|-----------|--------------|
| `outline-ready` | `bf-researcher` | Outline главы готов, `tonal_compass.md` актуален, пул источников собран; MATERIAL ещё не написан; готов к `bf-material-author` |

| `draft` | `bf-coordinator` (writer-loop exit) | Все beats accepted, `glava_NN.md` собран; готов к Editor (Контракт 9.1) |

## Правило размера MATERIAL (с 2026-05-07)

После INCIDENT-04 (Test3, MATERIAL_Glava_03_KS.md превысил 25К токенов на чтение):

- **Мягкий лимит:** ≤22 000 токенов на один MATERIAL.
- **Жёсткий лимит:** 25 000 токенов = дефект артефакта (превышение блокирует одношаговое чтение Read).
- **Защита:** §IX-предложения вынесены в `_verbot_liste_proposals_pending.md` (T14 session_template). Continuity-блок MATERIAL содержит только ссылку.
- **Если лимит достигается даже после §IX-staging** — выделить continuity-блок в отдельный файл `_continuity_Glava_NN_XX.md` (решается на ретроспективе книги).

## Правило размера Session-файла (с 2026-05-09)

После INCIDENT-07 (рецидивные обрывы compiler на Главе 1 KS, MATERIAL 76 КБ; гл.3–5 имеют MATERIAL 92–123 КБ):

Соответствующее правило размера MATERIAL зафиксировано выше (≤22К токенов мягкий, 25К жёсткий).
