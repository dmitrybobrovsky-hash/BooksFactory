# Повторный аудит BooksFactory — 2026-10-01

## 0. Резюме

**С 29 августа фабрика не менялась ни на байт.** Последняя правка рабочих файлов — 2026-05-16. Изменилась платформа: с начала августа вышло около 60 релизов Claude Code (около 30 — за сентябрь), новые модели (Sonnet 5.5 с 1M контекста — 28.09), и окончательно оформился инструмент **Workflow**, который решает ровно ту задачу, вокруг которой построена BooksFactory.

**Три главных вывода:**

1. **Августовский аудит подтверждается, но был мягче реальности.** Найдены четыре дефекта, которых он не заметил, и два из них критические: первый агент цепочки (`bf-researcher`) платформой **не загружается вообще**, а «изолированный» писатель (`bf-writer`) на деле имеет **все инструменты**, включая запись файлов и веб. Валидатор фабрики показывает «ЧИСТО» при наличии хардкода конкретной книги в координаторе.

2. **Сквозной прогон всё-таки был — частично.** Август писал «ни одной главы». Это неточно: writer-loop завершён на трёх главах (IU-01, KS-01 дважды), Введение KS прошло весь путь до `humanized` и немецкой версии. Не хватает прогона **текущей** версии v2.5 от начала до конца. Пилотная книга для него уже есть — «Карты на стол» (KS): шесть готовых MATERIAL, полный слой A.

3. **Главная проблема BF — оркестрация живёт в промптах.** Координатор (LLM) крутит цикл, компилятор (LLM) копирует файлы, критик (LLM) считает слова и ищет запрещённые фразы. Всё, что падало в Test3 (INCIDENT-04, 06, 07, 08), — следствие этого. Платформа сегодня предлагает обратное: **цикл — в коде (Workflow), механика — в скриптах, LLM — только для суждений.** Это не косметика, а смена несущей конструкции.

**MCP:** ядру фабрики MCP не нужны. На краях — проверка языка (LanguageTool) и экспорт; честность источников обеспечивает автоматическая сверка по каталогам. Подробно — §6.

**Рекомендуемый порядок:** сессия 0 (быстрые починки, ~1 час) → детерминированный слой → Workflow вместо координатора → сквозной прогон на KS → плагин, общий с TranslationFactory.

## 3. Новые находки

### Критические

#### N-1. `bf-researcher` не загружается платформой

Во фронтматтере нет поля `description`. По документации Claude Code такой файл **пропускается**, причина пишется только в debug-лог — в сессии ничего не видно. Агента `bf-researcher` для Claude Code не существует.

Файл правился 14.05 — после последнего прогона Test3, то есть сломан при параметризации v2.5 и с тех пор не запускался. Любой запуск «начни книгу» сегодня либо отработает основной сессией, прочитавшей файл как текст (без изоляции и ограничений инструментов), либо уйдёт в устаревший скилл `project-manager` (см. N-5).

→ Добавить `description`. Одна строка.

#### N-2. «Изолированный» писатель имеет все инструменты

`bf-writer.md`: в теле — «У тебя нет инструментов», в описании — «Zero filesystem tools». Во фронтматтере поля `tools` **нет**. По правилам платформы это значит: наследует **все** инструменты — Write, Edit, Bash, WebSearch, WebFetch, Agent.

Это тот же класс дефекта, что INCIDENT-06 (декларация ≠ реализация), но в более чувствительном месте: изоляция писателя — фундамент всей архитектуры writer-loop с независимым критиком.

Пустой список `tools` платформа не принимает (отказ запуска). Варианты: `tools: Read` как минимально безвредный набор, либо `disallowedTools` со всеми пишущими и сетевыми инструментами. Правильное решение — в целевой архитектуре (§7): writer вызывается из Workflow-скрипта с промптом, инструменты ему не нужны в принципе.

#### N-3. Хардкод книги KS в координаторе; валидатор его не видит

`bf-coordinator.md`, строки 255–256 — контракт вызова критика:

```
book_brief: <book>/anweisungen_KS.md, stil_und_ton_KS.md, case_protocol_KS.md
skvoznye_formuly: <book>/_skvoznye_formuly_KS.md
```

Для любой другой книги критик получит пути к файлам, которых нет, — и, судя по устройству критика, продолжит работу без брифа. Это прямое нарушение правила №8.

`validate_factory.py` при этом показывает «0 нарушений». Причина: шаблон `\b_KS\b` не срабатывает на `anweisungen_KS.md` — между `n` и `_` нет границы слова (оба — «словесные» символы). Валидатор структурно слеп к главному классу хардкода — суффиксу книги в имени файла.

→ Заменить на `<book>/anweisungen_<CODE>.md` с кодом из `book_config.json`; в валидаторе — шаблон `_(KS|IU|KNS|IG)\b` без ведущей границы.

### Серьёзные

#### N-4. `bf-controller` — мёртвый агент не на своём месте

При инициализации читает `BooksFactory/_TZ_WRITER_BEAT_BY_BEAT.md` и `BooksFactory/_HANDOFF_FACTORY_TUNING_2026-04-23_PART2.md`. Оба файла — в `archive/journal/`. По описанию он валидирует **фазы тюнинга фабрики** (Ф3, Ф7…), а не beat'ы. При этом `CLAUDE.md` ставит его в цикл `writer ↔ critic ↔ controller ↔ refiner`, а `production_state.md` — в переход `beat-N-accepted`. Самый большой агент фабрики (25 КБ) не может стартовать и описан в трёх местах по-разному.

→ Решить: удалить (функцию закрытия фаз выполняет автор) или переписать под проверку DoD главы. В целевой архитектуре его роль забирает детерминированная проверка в Workflow.

#### N-5. Устаревшие скиллы перехватывают запросы

В `.claude/skills/` 14 скиллов. Платформа видит все и сама решает, какой вызвать, по `description`. Проблемные:

| Скилл | Что описывает | Риск |
|---|---|---|
| `project-manager` | Роль PM (удалена 06.05), режимы research/compose, «Session_KapitelNN» | Запрос «новая книга», «следующая глава», «собери Session» уходит в устаревший процесс вместо `bf-researcher` (который к тому же не загружается — N-1) |
| `writer`, `draft-chapter` | Писатель «читает ОДИН файл — Session», пишет секция за секцией | Противоречит beat-модели; запрос «напиши главу» может обойти writer-loop |
| `connect-to-existing`, `synthesize-ideas`, `repurpose-to-*`, `generate-handout` | Эпоха Obsidian / контент-маркетинга | Шум в списке: каждый скилл — постоянная стоимость контекста и шанс ложного срабатывания |

→ Оставить только скиллы, которые запускают текущие этапы (`/bf-new-book`, `/bf-chapter`, `/bf-status`, `/bf-edit`, `/bf-humanize`) с `disable-model-invocation: true` — вызов только явно. Остальное — в архив. `/skill-doctor` покажет фактическую стоимость.

#### N-6. Контроль прав фактически выключен

Три слоя складываются:
- `.vscode/settings.json`: `"claudeCodeChat.permissions.yoloMode": true` (стороннее расширение VS Code);
- с v2.1.284 сессии по умолчанию стартуют в auto mode;
- `settings.local.json`: `Read(**)`, `Grep(**)`, `Glob(**)` без ограничения рабочей папкой.

Вместе с N-2 (writer с Write/Bash) и B-1 (хуки не работают) это значит: никакой механизм не мешает агенту записать файл куда угодно. Правило №0 («изоляция рабочей директории») держится только на послушании модели — именно оно и нарушалось в Test2.

→ Явно задать `permissions.defaultMode` и `deny` для путей вне `_outbound/<книга>` и папки фабрики; решить судьбу yoloMode.

#### N-7. Нет git

В корне нет репозитория. Следствия: (1) 21 снапшот полной копии фабрики вместо истории изменений; (2) недоступна `isolation: worktree` для агентов; (3) нельзя откатить одну правку агента точечно.

Оговорка: `.git` внутри OneDrive — известный источник конфликтов синхронизации. Варианты: репозиторий вне OneDrive с приватным remote на GitHub, либо исключение `.git` из синхронизации.

### Средние

- **N-8. Критик делает работу скрипта.** Из флагов `bf-critic` детерминированы: подсчёт слов, совпадения с `verbot_liste` (regex/substring — так и описано), лимиты «Паттерн ≤2», «сигнатурная фигура ≤8», обращение «ты/du», повтор фраз из `_skvoznye_formuly`. LLM в этом ошибается (INCIDENT-08 — ложные срабатывания). Это «пол», который должен проверять код, а критик — получать готовые цифры и судить о голосе.
- **N-9. Модели не зафиксированы осознанно.** Алиасы `opus`/`sonnet` сдвинулись на новое поколение без решения автора. Для воспроизводимости прогонов — указывать полный ID или хотя бы фиксировать в `book_config.json`, какие модели использовались. Поле `effort` не задано нигде.
- **N-10. Конституция грузится во все агенты.** `CLAUDE.md` и глобальный `~/.claude/CLAUDE.md` попадают в контекст каждого подагента, включая writer и critic, которым они не нужны и мешают «чистому взгляду» критика. Поле `omitClaudeMd: true` это снимает.

**Вывод для позиционирования.** Рынок «книга через Claude Code» за полгода заполнился, но на уровне «агент на главу». Beat-уровень с изолированным критиком, трёхзонная модель голоса, жанровые рубрики и verbot-слой — по-прежнему ни у кого. Дифференциатор BF жив, но отрыв сокращается, пока он не доказан прогоном.

## 6. MCP: что нужно, что нет

**Принцип:** ядро фабрики работает с локальными markdown/JSON-файлами — это встроенные инструменты Claude Code, MCP не нужен. MCP оправдан только там, где фабрика выходит наружу. Каждый сторонний MCP — код чужого автора с доступом к файлам; в январе 2026 даже официальный Git MCP от Anthropic получил три уязвимости. Ставить минимально.

### Рекомендуется

| MCP | Зачем | Связь с правилами BF |
|---|---|---|
| **LanguageTool MCP** (`dpesch/languagetool-mcp-server`; требует LanguageTool Pro или локальный сервер) | Грамматика и орфография DE/RU перед `bf-editor` и после `bf-humanizer` | Детерминированный «пол» для языка — редактор тратит внимание на смысл, а не на запятые |

Подключается **на уровне агента** (`mcpServers` во фронтматтере `bf-editor`), а не всей сессии.

> **Решение 2026-10-01: Zotero не используется.** Правило №1 обеспечивается автоматической сверкой: каждая позиция `quellen_pool` проверяется по библиотечным/книжным каталогам (автор, год, издание, ISBN), результат фиксируется в `SOURCES_VERIFIED_<CODE>.md`; в список попадают только подтверждённые данные. Пилот — KS (14 книг: 3 ошибки исправлены, 1 статья удалена). В сессии 1 сверка встраивается в фабрику как шаг после `bf-researcher`.

### Лучше скриптом, чем MCP

| Задача | Почему не MCP |
|---|---|
| Проверка существования книг (ISBN, Open Library) | Найденные MCP — платные скрейперы Apify. Открытый API Open Library вызывается из `tools/verify_sources.py` в 40 строк — детерминированно, бесплатно, без чужого кода |
| Экспорт DOCX/EPUB | `mcp-pandoc` существует, но pandoc из Python-инструмента (`tools/export.py`) проще и соответствует «только `python tools/*.py`» из TF |
| PDF | Уже решено: Playwright + Chromium |

### Не нужно

Filesystem MCP (встроено), Git MCP (git CLI безопаснее), Memory MCP (есть родное поле `memory:` у агентов), GitHub MCP (пока нет репозитория), sequential-thinking и подобные «усилители мышления» (модели 5.x делают это сами).

### Для чата-ревьюера на claude.ai

`Windows-MCP:FileSystem` остаётся рабочим. Связка «этот чат — ревью, Claude Code — исполнение» теперь может идти через привязку компьютера к сессии Claude (как в этом аудите) — без отдельного MCP.

## 7. Целевая архитектура v3

Принцип одной фразой: **код ведёт счёт и цикл, скрипты делают механику, LLM пишет и судит.**

### 7.1 Слои

```
                ┌─────────────────────────────────────────────┐
  автор  ──►    │  /bf-chapter KS 02   (скилл, явный вызов)   │
                └──────────────────────┬──────────────────────┘
                                       ▼
        .claude/workflows/write-chapter.js   ← цикл в коде
          phase("Prepare")  python tools/slice_context.py  (вместо bf-compiler)
          phase("Beats")    for beat in plan:
                               lint = python tools/lint_beat.py
                               text = agent(bf-writer, slice+prev2)      schema
                               v    = agent(bf-critic, text+lint)        schema
                               ≤3 итераций → manifest.py set beat accepted
          phase("Assemble") python tools/assemble_chapter.py
                                       ▼
                 _manifest.json  ← единственный писатель: скрипты
```

### 7.2 Что меняется по ролям

| Сейчас | v3 | Выигрыш |
|---|---|---|
| `bf-coordinator` (LLM, 20 КБ) крутит writer-loop | `write-chapter.js` | Цикл не забывает шаг, не теряет счётчик, возобновляется после обрыва; INCIDENT-06/08 невозможны как класс |
| `bf-compiler` (LLM, 23 КБ) собирает Session 175 КБ | `tools/slice_context.py`: для каждого beat — только его кусок MATERIAL, 2 предыдущих beat'а, выдержка голоса, релевантные запреты | Лимит размера исчезает; стоимость падает; INCIDENT-04/07 невозможны |
| `bf-critic` считает и ищет фразы | `tools/lint_beat.py` считает; критик получает цифры и судит о голосе, ритме, провокации | Меньше ложных флагов; критик дешевле (можно Sonnet 5.5 с `effort: medium`) |
| `production_state.md` вручную | `_manifest.json` + JSON Schema + `manifest.py` (порт из TF); markdown — генерируемое зеркало | Объект, который можно валидировать |
| `bf-controller` | удалить или DoD-проверка главы в фазе `Assemble` | −25 КБ мёртвого контекста |
| Хуки `bash … .sh` | `node ${CLAUDE_PROJECT_DIR}/.claude/hooks/*.mjs` в exec-форме (порт из TF) + хуки во фронтматтере агентов (`Stop` → `SubagentStop`: проверить, что агент оставил валидный артефакт) | Контроль работает на Windows и проверяет роль на выходе роли |

### 7.3 Настройки агентов

| Агент | tools | model / effort | Прочее |
|---|---|---|---|
| bf-researcher | Read, Grep, Glob, WebSearch, WebFetch, Write | opus / high | `description`(!), `mcpServers: [zotero]` |
| bf-material-author | Read, Grep, Write | opus / high | Stop-хук: размер MATERIAL, обязательные секции |
| bf-planner | Read, Write | opus / medium | Stop-хук: JSON beat-плана валиден по схеме |
| bf-writer | Read (минимум) | opus / high | `omitClaudeMd: true`, `cacheTtl: 1h` |
| bf-critic | Read | sonnet / medium | `omitClaudeMd: true`, `cacheTtl: 1h` |
| bf-editor | Read, Grep, Write | opus / high | `mcpServers: [languagetool]`, `disallowedTools: Edit` |
| bf-humanizer | Read, Edit, Write | opus / high | `skills: [humanizer-<lang>]` — подгружать модуль языка |

Все агенты ≤ 300 строк; справочный материал — в `skills/<роль>/references/`, читается по мере надобности.

### 7.4 Плагин `spellbooks-core`

Общий для BF, TF, EditorFactory: хуки (`read_gate`, `session_warden`, `sweep`, `final_guard`), `manifest.py`, `validate_factory.py`, `backup.py`. Локальный marketplace в `SpellBooks/`. Проверка — `claude plugin validate`. Убирает три копии одного слоя надёжности (риск из §4 августовского аудита).

## 8. План работ

### Сессия 0 — быстрые починки (~1 час, без перестройки)

1. `bf-researcher`: добавить `description` (N-1)
2. `bf-writer`: задать `tools` явно (N-2)
3. `bf-coordinator`: убрать `_KS` → `<CODE>`; `validate_factory.py`: исправить шаблон (N-3)
4. Минутный тест хуков (B-1, §7 августовского аудита). Если не работают — до порта на `.mjs` честно убрать их из `settings.json`: выключенный контроль лучше иллюзии контроля
5. Устаревшие скиллы → `archive/skills/` (N-5)
6. `CLAUDE.md`: статусы, нумерация, дерево — по `BOOKSFACTORY.md` (B-6, B-7, B-9)
7. `/doctor prompt-audit` и `/skill-doctor` — зафиксировать вывод
8. `git init` (решение по месту — §9)

После сессии 0 фабрика **работает в текущей архитектуре** — можно продолжать KS, не дожидаясь v3.

### Сессия 1 — детерминированный слой

`manifest.py` + схема (порт TF) · `slice_context.py` · `lint_beat.py` · `assemble_chapter.py` · `verify_sources.py` · расширенный `validate_factory.py` (фронтматтер агентов и скиллов, ссылки, статусы).

### Сессия 2 — Workflow

`write-chapter.js`; сжатие writer/critic; хуки `.mjs` + фронтматтерные Stop-хуки; удаление `bf-compiler` и writer-loop-части `bf-coordinator`.

### Сессия 3 — сквозной прогон на KS

- Глава 01 v2 (готова): editor → humanizer → final — закрывает путь главы целиком.
- Глава 02 (MATERIAL 93 КБ — выше старого порога 70 КБ, хороший тест для v3): полный путь через Workflow.
- Сравнить стоимость и качество с Главой 01 v2 (старая архитектура).

### Сессия 4 — модернизация

Плагин `spellbooks-core` · LanguageTool MCP · Режим B (Nachtrag 9.1) поверх манифеста: «слой A утверждён» = поле в `_manifest.json`.

## 10. Ограничения аудита

- Ни одного прогона не выполнено. B-1 подтверждён косвенно (§2), N-1 и N-2 — по документации платформы, а не по наблюдению.
